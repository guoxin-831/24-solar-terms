## 二、知识工程师：怎么拆关系

每个节气的 `phenology`、`custom`、`food` 都是 `；` 分隔的多值字段，直接 split 即可得到关系三元组：

```
立春 — 物候 — 东风解冻
立春 — 习俗 — 鞭春牛
立春 — 食俗 — 春饼
```

- 实体类型：节气、物候、习俗、食物、诗词。
- 关系类型：`has_phenology`、`has_custom`、`has_food`、`has_poem`，另加 `belongs_to_season`。
- 底线校验（计划书 3.2）：每个节气至少 1 条物候、1 条习俗、以及 1 条食俗或 1 首诗词——本表已全部满足。
- `custom` 平均 4.3 项/条，预计可拆出 100 条以上关系；`poem` 有 16 条为「未收录」，不要把它们建成节点。

## 三、AI 工程师：哪些字段进提示词

| 场景 | 取用字段 | 注意 |
|---|---|---|
| 节气介绍 | `name`、`term_rule`、`climate`、`phenology`、`custom`、`food` | 讲气候与物候时以 `climate`、`phenology` 为唯一事实来源 |
| 习俗问答 | `name`、`custom`、`region`、`sources` | 回答须带地域限定，不能把地方习俗说成全国通例 |
| 短口播 | 同「节气介绍」+ `poem` | `poem` 为「未收录」时不得补写诗句 |

**拒答规则**：用户问到表中没有的节气内容（如某地具体仪式细节），按计划书要求回答「资料未覆盖」，不得编造。字段为空或值为「未收录」时，一律视为未覆盖。

## 四、前端工程师：四个功能怎么接

| 功能 | 读什么 | 实现要点 |
|---|---|---|
| 总览（按四季） | `name` + `term_rule` | 表内无季节字段：按数组顺序每 6 个一季分组（1—6 春、7—12 夏、13—18 秋、19—24 冬）；交节时间显示 `term_rule` |
| 单节气详情 | 全部字段 | `phenology`/`custom`/`food`/`poem` 按 `；` 拆成列表项；`poem` 为「未收录」时显示为灰色标注，不要隐藏 |
| 关系浏览 | `phenology`/`custom`/`food` 拆分结果 | 用 `name` 与知识工程师的 `relations.json` 对齐（关系侧的 ST01—ST24 即按本表顺序生成） |
| 问答 | 由 AI 层返回，页面只负责展示 | 答案下方显示 `sources` 中的来源名，不显示完整 URL 长串 |

**加载示例**

```js
const terms = await fetch('data/solar_terms.json').then(r => r.json());
const SEASONS = ['春', '夏', '秋', '冬'];
const seasonOf = i => SEASONS[Math.floor(i / 6)];      // 顺序即季节，每 6 个一季
const spring = terms.filter((t, i) => seasonOf(i) === '春');
const lichun = terms.find(t => t.name === '立春');
const longitude = +lichun.term_rule.match(/黄经\s*(\d+)\s*°/)[1];   // 315
```

**不要做的事**：不要把 24 条数据硬编码进 HTML；不要自己改写字段名；不要为「未收录」的诗词补内容。

## 五、改数据怎么办

1. 只改 `data/solar_terms.json`，然后重新生成 CSV 与送审版表格；
2. 改完跑一遍 `docs/校验报告.md` 里的 C1—C7；
3. 源表无「更新日期」字段，改动时间记在交付说明与提交记录里；
4. 在群里说一声改了哪几条、影响哪些页面。第 2 周后只允许加字段，不改含义。
